## 1. 问题 2：卡片与搜索栏不同步

### 实测

```
卡片设置 impactBandPx=222, impactSpeedPps=4321, impactAccelPps2=1234
  -> 列表页完全正确：
     撞击测速区间：222 px     Enter 选择区间
     撞击速度：4321 px/s      Enter 选择门槛值
     撞击加速度：1234 px/s²   Enter 选择加速度门槛
```

所以**同步机制本身是好的**。问题在子菜单。

### 根因

`bandMenu()` 只列 `{50,80,120,150,200,300,500}`。卡片设 222，进 `cursorwrap band`：

```
实测：所有行 subtitle 都为空 -> 没有任何一行显示"当前"
```

同理 `accelMenu()` 只列 `{2000,5000,10000,20000,40000,80000}`，`speedMenu()` 只列 `{500,1000,2000,3000,5000,8000,12000,20000}`。

**而且我自己在 0.6.0 引入了一个必然踩中的坑**：`impactBandPx` 默认值从 150 改成 400，但 400 不在预设表里。也就是说**默认状态下打开 `cursorwrap band` 就没有一行高亮**。

### 方案

三选一（交互稿 [mockups/settings-sync.html](mockups/settings-sync.html) 有可点的三种）：

- **A（推荐）当前值恒有一行**：把手上的实际值插进列表并标记"当前"，即使它不在预设里。列表变成"你的值 + 预设值"。搜索栏能改回预设，也能看见自己的值。
- **B 常态显示"当前：X"行**：列表顶部固定一行只读的当前值。
- **C 卡片限制为预设值**：`plugin.json` 的 number 设置加 `options`，只允许预设。**不推荐** —— 用户就没法微调了，而调参正是这个插件的核心。

顺带：预设表里补上 `400`（新默认值）。`docs/review` 里列出的所有"默认值必须在预设里"要变成一条测试。

## 2. 问题 4：blocked 与 wrap 同时显示

### 根因（确定性，非竞态）

```cpp
// wrap_logic.cpp:505
if (withinGuard(sample.x, sample.y)) {
    m_verdict.guardBlocked = true;   // 只置这一位
    return skip(SkipReason::Guard);  // 直接返回
}
```

`m_verdict` 是**跨样本存活**的成员。上一次成功穿越时 `m_verdict.wrapped = true` 一直留着；下一次被守卫拦下，只把 `guardBlocked` 置 true，`wrapped` 仍是 true。

浮层于是同时画出：

```
guard · blocked     (橙色 caption + 橙色边框，来自 guardBlocked)
wrap                (绿色大字，来自上一轮的 wrapped)
```

### 实测

```
stroke 1400,540 -> 1919,540 ... landed 1,540 WRAP
move 1919,540 -> 1919,540 ...            <- verdict 里 wrapped 仍为 true
```

### 方案

`m_verdict` 必须**每个样本重建**，不是在旧值上打补丁。实现上：`onMouseMove` 开头 `m_verdict = EdgeVerdict{}`，然后各分支只填本样本的事实。另外 `wrapped` 与 `guardBlocked` 在结构上互斥，浮层再加一层断言（两者同时 true 时只画 blocked）。

## 3. 问题 3 / 6b：守卫链条（核心）

### 交互回放

[![guard](mockups/guard-chain.html)](mockups/guard-chain.html) — 四段**实测轨迹**，逐帧看守卫怎么拦、
怎么突然放行。直接打开 [mockups/guard-chain.html](mockups/guard-chain.html)。

### 现在的守卫有两条

```cpp
bool WrapEngine::withinGuard(x, y) const
{
    // (1) 离落点太近：防止刚穿越就穿回去     —— PowerToys 也有这条，合理
    if (m_hasLastWrap && dist(x,y, m_lastWrap) <= wrapGuardPx) return true;

    // (2) 仍压在同一条边上：视为"同一次到达"  —— PowerToys 没有这条
    if (m_hasWrapEdge) {
        away  = |x - m_wrapEdgeCoord|;        // 基准 = 那条边的精确坐标
        slack = max(edgeThresholdPx, 2);      // = 2
        if (away <= slack) return true;
    }
    return false;
}
```

### 缺陷 1：`slack` 只有 2 px — 与驱动抖动同量级（这是左右不对称的真正来源）

穿越在**阈值带内**触发，但守卫记的是**边的精确坐标**：

| 压的边 | 触发 | 守卫基准 `m_wrapEdgeCoord` | 错位 |
|---|---|---|---|
| 左 | `x <= left + edge` = `x <= 1` | `left` = `0` | 1 px |
| 右 | `x >= right-1-edge` = `x >= 1918` | `right-1` = `1919` | 1 px |

错位方向相反：右边缘的到达点在基准的**内侧**（1918 < 1919），左边缘的到达点在基准的**外侧**（1 > 0）。

更要紧的是 `slack = max(edgeThresholdPx, 2) = 2`。真实鼠标停在边缘时，驱动报的是钳制坐标 ±1 px 的抖动。
**2 px 的容差与 1 px 的抖动是同一个量级** —— 于是同一套手势，成败取决于那一两个像素：
`away = 2` 被拦、`away = 3` 放行。这就是"大部分时间不行、偶尔可以"。

实测：

```
stroke 到 1919 穿越，落点 1
move 1917 -> 无动作     away=2
move 1918 -> 无动作     away=1
move 1919 -> 无动作     away=0
move 1920 -> 无动作     away=1
move 1921 -> 无动作     away=2
move 1922 -> WRAP  ->1  away=3   ← 从这一像素起才放行
move 1923 -> WRAP  ->1  away=4
```

也就是说**必须离开 3 px 才能重新武装**，而 `slack` 是 2。

单屏（你的 RDP）把这件事放大：落点就在对边的阈值带里（压右 → 落点 `x=1`），于是落点守卫与边缘守卫**同时**
覆盖同一个位置，任何一点时间差都表现为"时灵时不灵"。

**RDP 可能是放大器（假设，待验证）**：本地鼠标是**相对位移**，`SetCursorPos` 之后 Windows 从落点继续
累加，下一条事件是 `x≈2`，落在落点守卫里，被拦住，不会重复穿越。远程桌面客户端送的是**绝对坐标**，
穿越后客户端那边的物理指针仍在边缘，服务端下一条事件可能直接就是 `x=1930`。
如果成立，这就是为什么你在 RDP 下遇到、本地双屏不明显。

**验证方法（不改代码）**：`cw_devshell` 跑同样的序列已经是"每次事件都是绝对坐标"，上面 A 段就是这样复现的。
真机确认只需打开数据窗口看 `SetCursorPos` 失败计数与 wrap 计数是否同时上涨。这条我列进测试计划，不当作结论。

### 缺陷 2：`m_hasWrapEdge` 的清零点在守卫之后

`m_hasWrapEdge` 只有在样本**不**被守卫拦下时才被清（`wrap_logic.cpp:511` 那段）。而手压着边缘时，
样本恰好全被守卫拦下 —— 于是这个闩锁**永远不会自己解除**。

```
实测：stroke 到 1919 穿越 -> 之后 move 1920/1930/1950 继续推
      1920 -> 1920,540        (被守卫拦)
      1930 -> 1,540  WRAP     (离开 11 px，重新武装后立刻又穿)
      1950 -> 1,540  WRAP
```

这就是你说的**"穿越后指针飞远"**：手还在往右推，指针被反复拽回 `x=1`，视觉上像被甩飞。PowerToys 只有落点守卫，落点在 `x=1`，而手在 `x=1930`，相距 1929 px，所以它**也会**再穿一次 —— 但它不会出现"同一条边上永远不重新武装"。

### 缺陷 3：`wrapped` 不随守卫清除 → 问题 4

见上一节。

### 方案

**把两条守卫合并成一条，用"离开落点"作为唯一的重新武装条件**（即 PowerToys 的语义），并额外加一条**时间冷却**来覆盖"手压着边缘不断重发同一点"的情况：

```
武装条件（全部满足才允许穿越）
  A. 距上次落点 > wrapGuardPx             （空间，已有）
  B. 距上次穿越 > cooldownMs（建议 120）    （时间，新增）
  C. 行程（可选，见下）

删掉：m_hasWrapEdge / m_wrapEdgeCoord / slack（与 edgeThresholdPx 错位的那个）
```

为什么 A + B 够：A 挡住"刚穿越就穿回去"，B 挡住"手压着边缘不断重发同一点"。
当前那条被删的检查想做的事，本质上就是 B —— 只是它用**空间**去表达**时间**，于是和抖动打架。

> **风险与不猜的部分**：`tests/scenarios/gate-off-churn.txt` 断言"沿底边滑动一次都不穿"。
> 现在这条是靠**方向判定**（`onOuterEdge` 的 `prioritize` 按主运动轴挑边）保住的，实测沿上/下/中三条线
> 滑 40 步均 0 次穿越，与那条守卫无关。所以删掉边缘带守卫**不会**破坏这个场景 —— 但我会先跑确认，
> 见第 6 节。
>
> C（行程）这一条我还没验证它是否会和"手压边缘微抖"冲突：抖动 ±1 px 累积起来能超过一个阈值。
> **所以我建议先只做 A + B**，把 C 作为可选项，用场景数据说话。

## 4. 问题 5：加速度读数

### 5a 「一直 1600」其实是"测不到"

浮层画的是 `accel <测量值> / <门槛>`。`— / 1600` 意思是**斜率测不出来**，不是"值等于 1600"。0.6.0 我把它改成 fail-closed（测不到就拒绝），所以**开着撞击模式时几乎永远不穿越**。

实测为什么测不到：

```
hand 800->3000 px/s  125Hz  75 samples  -> speed=0     accel=0      no-wrap
hand 800->3000 px/s  500Hz 300 samples  -> speed=0     accel=0      no-wrap
hand 800->3000 px/s 1000Hz 600 samples  -> speed=0     accel=0      no-wrap
hand 1600->3000 px/s 125Hz  32 samples  -> speed=1687  accel=3479   no-wrap（被速度门槛挡住）
```

要求是：加速度窗口 ≥ `kImpactAccelMinWindowUs` = **12 ms**，且**两半各需 ≥ 4 px 行程**。手在离边 400 px 的带内、以 2000 px/s 走，只花 200 ms —— 够。但 `hand` 前三条根本没到达边缘（`landed=1348`），因为 600 ms 内没走完。第四条到达了、也测到了 `3479`，但 `speed=1687 < 2000` 被速度门槛先挡住。

结论：**算法能测，但"速度门槛 + 加速度门槛"两把锁同时开着时，可用区间极窄**。这是设计问题，不是 bug。

### 5a 方案（交互稿 [mockups/readout.svg](mockups/readout.svg)）

- 浮层文案改成明确的三态：`加速 +3479 ✓` / `加速 −6227 刹车` / `加速 测不到`。不要用 `—` 这种要靠猜的符号。
- 加一行**建议**：两把锁同时开时给出"当前手势可穿越区间"，直接告诉用户该把门槛设多少。
- 更根本的一步：**默认只开一把锁**。速度门槛与加速度门槛是两种不同的手势判据，同时要求"够快"且"还在加速"会把绝大多数真实动作排除掉。建议 `impactAccelPps2` 默认保持 0（现状），并在设置卡里写明"开启后建议把速度门槛下调"。

### 5b 文字被边框切掉

```
constexpr int kReadoutH = 60;
TextOutW(dc, 10, 46, line, ...);   // 13 px 字体，基线 46，落到 ~59
底边框画在 {0, h-2, w, h} = y 58..60
```

**13 px 字体从 y=46 起，行高约 17 px，占 46..63，越过 58..60 的边框并出窗。** 实测截图就是这个。

方案：浮层高度按行数算，不写死 60。两行 = 标题 13 + 主值 24 + 次值 13 + 上下内边距 → 约 74 px；三行再 +17。或者干脆把加速度行画在**主值右侧**同一行（宽度 196 够放 `0 / 3000 px/s ` 但要缩字号）。交互稿里两种都画了。

## 5. 问题 6a：穿越光效（新功能）

需求：撞击模式穿越后，边缘有一道短暂光效；可配置，**默认关闭**。

设计（[mockups/overlay-effects.html](mockups/overlay-effects.html) 可交互预览）：

- 触发：只在**成功穿越**且 `impactGate` 开启时。
- 位置：贴着被压的那条边，从落点沿边展开约 `min(边长, 40%)`，不是整条边（整条边会像警告）。
- 时长：180 ms，缓出（`opacity: 1 → 0`，`scale` 不变，避免"闪一下"）。
- 颜色：跟随宿主 `accent`，撞击成功用正向色，被拒绝时可选画一道极淡的灰（默认不画）。
- 实现：复用 `Overlay` 已有的分层窗口（`m_bandPx` 那套），新增一个 `impactFlash` 层，一条 2–3 px 的渐变条。**不新增窗口**，否则每块屏一个窗口。
- 新设置：`impactFlash`（bool，默认 false）、`impactFlashColor`（choice：accent / warm / cool）。
- 约束：光效必须**不拦截鼠标**（`WS_EX_TRANSPARENT`，与现有层一致），且失败时静默 —— 光效是装饰，不能因为它出错而影响穿越。

## 6. 测试方案

原则：**先写红，再改。** 每条修复都有一个会失败的场景。

### 6.1 守卫链条（问题 3 / 4 / 6b）

新场景 `tests/scenarios/guard-rearm.txt`：

| 断言 | 现在 | 修复后 |
|---|---|---|
| 慢推（1 px/16 ms）到左边 → 穿越 | 通过 | 通过 |
| 慢推（1 px/16 ms）到右边 → 穿越 | 通过 | 通过 |
| **左右对称矩阵**：左右两条边 × 4 个 y × edge 1/2/5，结论完全一致 | 部分 | 全部 |
| 压边穿越后再压同一条边（不离边）→ 不重复穿越 | 通过 | 通过 |
| 穿越后继续同向推进 30/50/100 px → **不**重复穿越 | **失败** | 通过 |

| `SetCursorPos` 失败后同一条边能立刻重试 | 通过（0.6.0 已修） | 通过 |

最后一条用 L1 单元测试最稳：遍历 2000 个随机样本序列，断言任意时刻 `verdict.wrapped && verdict.guardBlocked` 为假。

### 6.2 设置同步（问题 2)

新 L3 检查（`tests/protocol_roundtrip.py`）+ 新单元测试：

- 卡片设 `impactBandPx=222` → 进 `cursorwrap band` → **恰好一行有 subtitle**，且标题含 `222`。
- 对全部 13 个设置 × `{默认值, 最小, 最大, 一个非预设值}` 做矩阵。
- 断言：`plugin.json` 里每个 number 设置的 `default` 必须能在对应子菜单里找到高亮行。

### 6.3 浮层（问题 5b）

无法在单元测试里量文字，所以：`kReadoutH` 改成由行数算出的函数，单元测试直接断言"计算高度 ≥ 各行内容底 + 4 px 内边距"。再加一个 devshell 的 `--script` 截图，人工确认一次。

### 6.4 光效（问题 6a）

单元测试：`impactFlash` 关闭时不创建层；开启时只有在 `impactGate && wrapped` 时创建；层带 `WS_EX_TRANSPARENT`；`SetLayeredWindowAttributes` 的 alpha 序列单调递减。

### 6.5 回归门槛

改完必须全绿：`cw_tests`（当前 155）、12 个场景（会变 13）、协议 123、`validate.py`。

## 7. 需要你确认的三点

1. **守卫方案**：接受"删掉边缘带检查（`m_hasWrapEdge`）、改用 空间 + 时间两重武装"吗？行程那一条我建议先不做。
   实测已确认沿边滑动靠**方向判定**保住、与这条守卫无关，所以风险比我原先估的**低**。
2. **加速度门槛默认**：保持 0（只开速度门槛）？还是在设置卡里标成"高级/实验"并默认收起？
   现状是 0 = 关闭，但它和速度门槛同时开启时可用区间极窄（见 5a），这是设计取舍。
3. **光效**：默认关闭（我建议），还是默认开启但极淡？

版本：行为变更 + 新功能，按 minor 走 **v0.7.0**。
